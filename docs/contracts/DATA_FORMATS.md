# Форматы данных

Этот документ описывает форматы массивов, таблиц и дисковых хранилищ. Большое ТЗ v7 — основной источник требований. Неизвестные детали помечены как `TBD`; это не готовые контракты и не разрешение выбирать значения самостоятельно.

## 1. Общие правила

Ниже приведены форматы, которые описаны в предшествующем интерфейсном документе или присутствуют в реализации репозитория.

Точные диск-форматы и схемы считаются не подтверждёнными до сверки с ТЗ и согласования командами.

### Используемые форматные классы

| Формат | Назначение | Текущее состояние |
|---|---|---|
| Исходные файлы L1B | Загрузка VIIRS/SLSTR | Формат входных продуктов определяется источниками данных; детали интеграции остаются открытыми |
| Zarr | Промежуточные массивы и история фона | Упоминается в ТЗ v7; структура и параметры хранения требуют отдельного контракта |
| GeoParquet | Таблицы обнаружений и событий | Поля и часть правил хранения обнаружений сверены с ТЗ v7; writer отсутствует |
| JSON | Отчёт качества и файлы текущего каркаса | Секция `validation` HS-01 реализована; полный формат отчёта открыт |
| SQLite | Пиксельный журнал текущего каркаса | Используется существующим кодом; схема и сроки хранения не утверждены этим документом |

## 2. Общие правила отсутствующих значений

| Правило | Текущее состояние |
|---|---|
| Ноль — измеренное значение, а не признак пропуска | Не заменять отсутствующие данные нулём |
| `NaN` и бесконечность | Не использовать как значения HS-01: числовые поля модели отклоняют нефинитные значения |
| Nullable-поля обнаружения | Только `event_id`, `b_hist` и `q_hist`; история должна согласовываться с `n_hist` |
| Коды `fill_value` для массивов | Не определены; требуется контракт соответствующего формата |
| Нет наблюдения и ясное наблюдение без обнаружения | Должны различаться; точная схема передачи остаётся открытой |

## 6. GeoParquet обнаружений

Таблица сверена с ТЗ v7, разделами 3.1 и 6.5.4. Одна строка соответствует одному пикселю после статистического решения.

| Поле | Тип в хранилище | Единицы и назначение |
|---|---|---|
| `det_id` | uint64 | детерминированный идентификатор из платформы, времени, строки и столбца |
| `platform` | string, dictionary | `NOAA-20`, `NOAA-21`, `S-NPP`, `S3A`, `S3B`, `S3C` |
| `sensor_view` | string, dictionary | `VIIRS_I`, `VIIRS_M`, `SLSTR_nadir`, `SLSTR_oblique` |
| `t_utc` | timestamp, миллисекунды | UTC, без часового пояса |
| `lat`, `lon` | float64 | градусы; центр пикселя |
| `footprint` | WKB Polygon | след пикселя, координаты EPSG:4326 |
| `granule` | string | идентификатор гранулы |
| `line`, `sample` | integer | положение пикселя в грануле; Python-модель HS-01 проверяет диапазон int32 |
| `area_m2` | float32 | м² |
| `scan_angle`, `vza`, `sza`, `raa`, `glint_angle` | float32 | градусы |
| `stratum` | string, dictionary | страта раздела 5.7.2 |
| `T_mir`, `T_tir` | float32 | K |
| `mir_channel` | string | `I4`, `M13`, `S7`, `F1` |
| `r_block`, `r_win`, `s_win` | float32 | K |
| `h_lev` | float32 | безразмерный рычаг пикселя |
| `b_hist`, `q_hist` | float32, nullable | исторические медиана и масштаб, K |
| `n_hist` | integer | неотрицательное число наблюдений |
| `s_eff` | float32 | K |
| `z` | float32 | безразмерный нормированный остаток |
| `p_value` | float32 | вероятность, больше 0 и не больше 1 |
| `nfa_pixel`, `nfa_cluster`, `nfa_multi` | float32 | число ложных тревог |
| `significance` | float32 | `-lg(min NFA)` |
| `decision` | string, dictionary | `confirmed`, `needs_confirmation`, `rejected` |
| `frp_mw`, `frp_err_mw`, `frp_toa_mw`, `frp_50_mw` | float32 | МВт |
| `flags` | uint32 | битовая маска качества |
| `event_id` | string, nullable | идентификатор события |
| `source_class` | string, dictionary | `vegetation_fire`, `persistent_industrial`, `persistent_natural_candidate`, `recurrent_seasonal`, `volcano_candidate`, `unknown` |

Все измерения хранятся как float32; координаты — как float64. Строки с малым числом значений кодируются словарём. Файлы разбиваются по месяцам и упорядочиваются по времени, затем по номеру ячейки рабочей сетки.

По уточнению для HS-01 `event_id` допускает null до привязки обнаружения к событию. `b_hist` и `q_hist` допускают null при отсутствии истории, что должно сопровождаться `n_hist == 0`; при наличии исторических наблюдений оба поля обязательны. Для остальных полей модели null не допускается.

Модель Python и JSON-представления описаны в [JSON-контракте HS-01](JSON_CONTRACT.md). Pydantic проверяет значения и ограничения типов, но физическую запись GeoParquet (включая dictionary encoding, timestamp без часового пояса и CRS в метаданных) должен выполнять отдельный слой хранения. WKB сам по себе не подтверждает CRS.

ТЗ требует детерминированно формировать `det_id`, но не задаёт раскладку битов или точный алгоритм. Текущий валидатор проверяет только uint64; генератор и физическая Arrow-схема остаются отдельной задачей. Ширина физических целочисленных типов, не заданная ТЗ, остаётся открытым вопросом CQ-06.

## 6.1 Секция валидации отчёта качества

Структура `validation` реализована для HS-01. Она содержит `valid_count`, `invalid_count`, `errors` и `warnings`. Коды ошибок и JSON-примеры приведены в [JSON-контракте HS-01](JSON_CONTRACT.md) и [справочнике ошибок валидации](VALIDATION_ERRORS.md).

Секция фиксирует результаты проверки записей обнаружения, но не определяет остальные поля отчёта качества. Ошибки отдельной записи возвращаются результатом валидации; ошибки сериализации и записи файла логируются и пробрасываются вызывающему коду. Общая схема верхнего уровня остаётся открытой до решения CQ-07.

## 8. Геопривязка и координатные системы

ТЗ v7 указывает WGS 84 (EPSG:4326) для таблиц обнаружений. Модель HS-01 проверяет корректность WKB и тип `Polygon`, но не делает выводов о CRS по содержимому WKB.

CRS рабочей проекции, эталонной сетки и геометрии полосы остаются открытыми вопросами CQ-10. Их нельзя выводить из проверки footprint.
