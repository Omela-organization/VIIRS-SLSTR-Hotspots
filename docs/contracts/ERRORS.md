# Обработка ошибок

## 1. Категории ошибок

Перед обработкой исключения разделяются по тому, на каком этапе возникла проблема.
Это позволяет остановить обработку в критичных случаях и продолжить её при изолированной необязательной ошибке.

Следующие категории — предложения для общей системы обработки ошибок; специализированные классы исключений в проекте пока не реализованы. Исключение составляет валидация HS-01, которая использует `pydantic.ValidationError` внутри валидатора и возвращает структурированный результат.

| Категория | Назначение | Статус |
|---|---|---|
| ConfigurationError | Некорректная конфигурация | PROPOSED |
| InputDataError | Повреждённый или несовместимый вход | PROPOSED |
| MissingDataError | Отсутствуют обязательные данные | PROPOSED |
| ValidationError | Нарушен контракт данных | PROPOSED |
| ProcessingError | Ошибка вычисления | PROPOSED |
| StorageError | Ошибка записи/чтения | PROPOSED |
| ExternalServiceError | Недоступность внешнего источника | PROPOSED |

Создание новых классов исключений не выполнялось. Не следует реализовывать перечисленные имена без отдельного согласования Task ID.

## 2. Ошибки конфигурации

Примеры:

- отсутствующий обязательный файл конфигурации;
- несовместимое значение параметра;
- неизвестный модуль или нарушение диапазона;
- несовместимые параметры сетки;
- невалидная deployment-конфигурация.

Ожидаемое логирование и полный набор исключений — TBD.

## 3. Ошибки входных данных

Примеры старого документа:

- повреждённый или неизвестный формат продукта;
- неполный набор гранул;
- несоответствие контрольной суммы;
- отсутствие геопривязки;
- отсутствие СХК;
- несогласованные размеры массивов;
- неизвестный формат флагов прибора.

При неполном наборе нельзя молча считать данные полноценными.

**Статус:** PROPOSED.

## 4. Ошибки обработки

Примеры:

- недостаточно годных пикселей;
- невозможно оценить фон;
- невозможно подобрать хвост распределения;
- некорректная геометрия окна;
- ошибка кригинга;
- невозможность сохранить суммарную FRP.

Точные условия stop/continue и коды ошибок — TBD.

## 5. Ошибки записи результатов

Примеры:

- каталог недоступен;
- ошибка записи Zarr;
- ошибка записи GeoParquet;
- ошибка записи JSON отчёта;
- частично записан продукт;
- несоответствие контрольных метаданных.

`QualityReport` записывает JSON через временный файл и заменяет целевой файл атомарно. Ошибки сериализации и файловой системы логируются и передаются вызывающему коду. Общая политика отката и повторов для остальных хранилищ не определена.

**Статус:** TBD.

## 6. Ошибки интеграции модулей

Текущий каркас передаёт словари путей к JSON-файлам через `runner.py`. Формат содержимого этих файлов не определён и не является согласованным контрактом.

Проверки должны включать:

- совпадение размерностей;
- совпадение ожидаемых каналов и полей;
- соответствие dtype;
- корректность временных меток UTC;
- корректность CRS;
- наличие обязательных значений;
- корректность маски качества;
- отсутствие молчаливой замены NaN нулём;
- сохранение суммы FRP при сеточном пересчёте.

**Статус:** PROPOSED для проверки и TBD для механизма интеграции.

## 7. Логирование

Зависимость `structlog` указана в `pyproject.toml`, однако единая конфигурация логирования не обнаружена. HS-01 использует стандартный модуль `logging` для ошибок сериализации и записи отчёта.

Диагностическое сообщение должно содержать минимально:

- идентификатор или контекст модуля;
- идентификатор пролёта, если известен;
- тип ошибки;
- понятное описание причины;
- входные значения/пути только в безопасном объёме;
- рекомендации по восстановлению, если доступны.

Политика секретов и уровни log — TBD.

**Статус:** PROPOSED.

## 8. Остановка и продолжение

Предшествующий документ предлагает продолжать обработку при состояниях, не мешающих выдаче результата, и останавливать обработку при невозможности корректного выхода.

Точный перечень ошибок остановки, повторов и continue-политики — TBD.

Правило: нельзя молча перехватывать исключение и продолжать с некорректным набором данных.

Для HS-01 ошибка отдельной записи обнаружения возвращается как `valid: false` с `can_continue: true`; запись пропускается, и следующие записи можно проверять. Ошибки сериализации и записи отчёта не преобразуются в ошибки записи и пробрасываются вызывающему коду. См. [VALIDATION_ERRORS.md](VALIDATION_ERRORS.md).

## 9. Существующая реализация

В `runner.py` реализованы регистрация и вызов шагов. HS-01 предоставляет валидатор и накопитель отчёта; поиск по пакету не обнаружил вызовов `validate_detection_record()` из шагов M0–M11. Интеграция валидатора в конвейер остаётся отдельной задачей.

Текущий runtime-контракт может быть изменён только в рамках Task ID, не формулирующего автоматически новые исключения.
